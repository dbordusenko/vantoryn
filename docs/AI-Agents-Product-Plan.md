# Vantoryn AI Agents — План продукта и база требований для ТЗ

**Статус:** черновик v0.1 (research-based)
**Дата:** 2026-08-10
**Автор:** подготовлено на основе анализа реальных вакансий (FP&A, Financial Controller, Treasury, AP/AR) + рынка агентных AI-решений в финансах 2026.

---

## 1. Идея продукта

Отдельный продукт (`Vantoryn Agents`) — набор автономных AI-агентов, каждый из которых
воспроизводит функции конкретной финансовой роли: **Финансовый аналитик (FP&A)**,
**Контролёр (Controller)**, **Казначей (Treasury)**, **Специалист AP/AR**.

Агенты не заменяют человека целиком, а закрывают **рутинный 60–80% объём** работы роли
(сбор данных, сверки, вариативный анализ, черновики отчётов, алерты), оставляя человеку
решения и коммуникацию. Это прямое развитие существующего APS-движка Vantoryn: у нас уже
есть оптимизационное ядро и cash-flow пайплайн — агенты становятся «умным слоем» поверх него.

**Ключевой тезис для позиционирования:** Gartner прогнозирует, что к 2026 г. 90% финансовых
функций внедрят хотя бы одно AI-решение. Спрос на финансовых аналитиков в 2024 вырос на 59% —
рынок перегрет, найм дорогой, что делает «агента-аналитика» экономически привлекательным.

## 2. Ростер агентов (роль → что делает агент)

| Агент | Прообраз-роль | Что автоматизирует |
|-------|---------------|--------------------|
| **Analyst Agent** | FP&A Analyst | Бюджеты, rolling-прогнозы, вариативный анализ, финмодели, сценарии |
| **Controller Agent** | Financial Controller | Month-end close, сверки GL/AP/AR, контроль внутренних процедур, черновик отчётности, флаги аномалий |
| **Treasury Agent** | Treasury Analyst | Прогноз ликвидности (кратко/долгосрочный), позиция по кэшу, платёжный календарь, FX/процентные риски |
| **Ledger Agent** | AP/AR Specialist | Кодирование счетов, сверка инвойсов, aging-отчёты, напоминания по просрочке, детект дублей платежей |

## 3. База требований из вакансий (сырьё для ТЗ)

| Variance Analysis — сравнение факт vs бюджет/прогноз, поиск корневых причин, рекомендации | Авто-variance с driver-attribution + текстовый комментарий | P0 |
| Мониторинг операционных данных, отчёт по трендам/отклонениям/проблемам | Continuous monitoring + алерты на аномалии выручки/расходов | P1 |
| Анализ по бизнес-юнитам, сегментам, географии, M&A | Разрез-анализ по измерениям | P1 |
| Attention to detail, accuracy, работа в жёсткие дедлайны | Валидация данных перед расчётом, аудит-трейл | P0 |

### 3.2 Controller Agent

| Обязанность из вакансии | Capability агента | Prio |
|---|---|---|
| Оверсайт day-to-day бухгалтерии: billing, AR, AP, GL, cost accounting, revenue recognition, inventory | Оркестрация над Ledger/AP-AR данными, единый статус закрытия | P1 |
| Подготовка месячной отчётности и P&L | Черновик income statement / management pack | P0 |
| Month-end close: журнальные проводки, интеркомпани-сверки, variance-комментарии | Автоподготовка проводок, сверок; сжатие close с недель до дней | P0 |
| Monitoring internal controls | Правила-контроли + флаги нарушений (segregation of duties, лимиты) | P1 |
| Evaluating and managing risk, coordinating audit | Аудит-трейл всех действий агента, экспорт для аудита | P0 |
| Compliance-oriented mindset, знание отчётных требований | Конфигурируемые правила по стандарту (US GAAP/IFRS/РСБУ) | P2 |

### 3.3 Treasury Agent

| Обязанность из вакансии | Capability агента | Prio |
|---|---|---|
| Ежедневный cash management, мониторинг позиции по кэшу | Дэшборд позиции по кэшу в реальном времени | P0 |
| Кратко- и долгосрочный прогноз денежных потоков | Cash-flow forecast (уже частично есть в APS) | P0 |
| Reconcile forecast variances с бизнес-юнитами | Сверка прогноз vs факт, объяснение отклонений | P1 |
| Управление платёжным календарём и графиками платежей | Платёжный календарь + приоритезация | P1 |
| Идентификация рисков ликвидности, %, FX | Риск-алерты (кассовый разрыв, ковенанты, FX-экспозиция) | P1 |
| Compliance: reporting requirements, financial regulations, tax | Проверки по правилам, отчётные шаблоны | P2 |

### 3.4 Ledger Agent (AP/AR)

| Обязанность из вакансии | Capability агента | Prio |
|---|---|---|
| Обработка инвойсов, ведение записей вендоров, подготовка платежей | AI-кодирование инвойсов (GL/cost center/проект) с учётом PO/контракта | P0 |
| Предотвращение дублей и просрочек платежей | Детект дублей, алерты по дедлайнам | P0 |
| Выставление счетов клиентам, учёт платежей, aging-отчёты, follow-up | Авто-aging + черновики напоминаний | P1 |
| Сверка AP/AR, разрешение расхождений | Матчинг 2-way/3-way (инвойс–PO–receipt), список расхождений | P0 |
| Отчёты для менеджмента по cash flow / aging | Готовые отчёты по требованию | P1 |

### 3.5 Сквозные (не-функциональные) требования

Извлечено из повторяющихся требований в вакансиях всех ролей:

- **Точность и аудит:** «attention to detail with emphasis on accuracy» → каждый вывод агента
  трассируется до исходных данных; ни одной цифры «из ниоткуда».
- **Конфиденциальность:** «ability to maintain confidentiality» → изоляция данных клиента,
  без утечки в обучение, RBAC.
- **Работа в дедлайны:** «tight deadlines», «additional hours during close» → SLA на отклик,
  расписания (close-календарь phase 1–4).
- **Интеграции:** proficiency in accounting software → коннекторы к 1С/ERP/учётным системам,
  импорт CSV (уже есть в Vantoryn), банковские выписки.
- **Коммуникация:** «strong communication» → человекочитаемые объяснения, а не только числа.

## 4. Архитектура (высокоуровнево)

```
┌─────────────────────────────────────────────────────────┐
│                    Orchestrator (Controller)              │
│  планирует задачи, распределяет между агентами, close cal │
└───────────────┬───────────────┬───────────────┬──────────┘
        ┌───────┴──────┐ ┌──────┴───────┐ ┌─────┴────────┐
        │ Analyst Agent│ │Treasury Agent│ │ Ledger Agent │
        └───────┬──────┘ └──────┬───────┘ └─────┬────────┘
                └────────────────┼───────────────┘
                         ┌───────┴────────┐
                         │  Tool layer     │   ← детерминированные инструменты
                         │  (не галлюцинир.)│      (расчёты делает код, не LLM)
                         └───────┬────────┘
        ┌────────────────┬───────┼────────┬──────────────┐
   APS-движок      Data connectors   Vector store    Audit log
  (OR-Tools)      (ERP/1C/bank/CSV)  (политики/доки)  (трассировка)
```

**Принцип «числа считает код, LLM объясняет»:** LLM оркестрирует и формулирует, но все
финансовые вычисления идут через детерминированные инструменты (наш APS-бэкенд, формулы) —
это снимает риск галлюцинаций в цифрах, критичный для finance.

**Стек (предложение, поверх текущего):**
- Оркестрация агентов: Claude API (tool use / agent loop) — у нас уже Anthropic-инфраструктура.
- Инструменты: расширение существующего FastAPI-бэкенда (`aps-backend/`).
- Память/контекст: pgvector или аналог для политик и исторических комментариев.
- Фронт: переиспользуем React-компоненты Vantoryn (дэшборды, чарты).

## 5. Поэтапный план (roadmap)

### Фаза 0 — Discovery & ТЗ (2–3 нед)
- Финализировать требования из §3 в формальное ТЗ.
- Выбрать 1 «якорного» агента для MVP — **рекомендация: Analyst Agent (FP&A)**, т.к.
  вариативный анализ + прогноз дают самый быстрый видимый ROI и уже частично покрыты APS.
- Определить 1 пилотный источник данных (CSV/1С) и 1 пилотного клиента.

### Фаза 1 — MVP: Analyst Agent (6–8 нед)
- Коннектор данных → нормализация → APS-пайплайн.
- Capabilities P0: variance analysis с driver-attribution, rolling forecast, генерация комментария.
- Аудит-трейл + UI в кабинете Vantoryn.
- Критерий успеха: агент за минуты выдаёт variance-пакет, который аналитик делал за день.

### Фаза 2 — Controller + close-оркестрация (6 нед)
- Close-календарь (phase 1–4), черновики проводок, сверки, management pack.
- Внутренние контроли и флаги аномалий.

### Фаза 3 — Treasury + Ledger (8 нед)
- Прогноз ликвидности, платёжный календарь, риск-алерты.
- AI-кодирование инвойсов, 3-way match, aging + follow-up.

### Фаза 4 — Мультиагентная оркестрация (ongoing)
- Агенты обмениваются данными (Ledger → Treasury → Analyst), Controller координирует.
- Расширение коннекторов, стандарты отчётности (GAAP/IFRS/РСБУ).

## 6. Риски и открытые вопросы

- **Доверие к цифрам** — снимается архитектурой «код считает, LLM объясняет» + аудит-трейлом.
- **Данные клиента / комплаенс** — RBAC, изоляция, отказ от обучения на данных клиента.
- **Интеграции** — самая трудоёмкая часть; для MVP ограничиться CSV + одним ERP.
- **Ответственность** — агент даёт черновик/рекомендацию, финальное решение за человеком (важно юридически).
- **Открытый вопрос:** целевой сегмент (SMB vs enterprise) и стандарт учёта пилота — влияет на приоритет P2-требований.

## 8. MVP: критерии приёмки и метрики качества

Без измеримых порогов «MVP готов» — не инженерное утверждение. Для якорного Analyst Agent:

| Метрика | Порог MVP | Зачем |
|---|---|---|
| Точность variance vs эталон аналитика | MAE / SMAPE в согласованном коридоре на пилотном датасете | Доказать, что цифрам можно доверять |
| Покрытие driver-attribution | ≥ 90% отклонения объяснено драйверами | Иначе комментарий бесполезен |
| Полнота аудит-трейла | 100% выводов трассируются до исходной строки данных | Требование всех finance-ролей |
| Latency пакета variance | целевой диапазон (напр. < сек. на расчёт, минуты на пакет) | vs день ручной работы |
| Data validation pass rate | 100% входа проходит валидацию до расчёта | «garbage in» не доходит до ядра |

Тестирование: unit на инструментах-расчётах (детерминированные, легко покрыть), golden-набор
«вход → ожидаемый variance-пакет» для регрессии, end-to-end на пилотных данных.

## 9. Data Validation Layer (выделено явно)

Отдельный слой **перед** APS-ядром — не опция, а часть контура доверия:

- **Schema-валидация** входа (типы, обязательные поля, периоды).
- **Checksums / контроль сумм** (баланс сходится, subtotal = Σ строк).
- **Fuzzy-matching** справочников (счета, вендоры, cost-центры) при импорте из разных систем.
- **Карантин** невалидных строк с человекочитаемым отчётом, а не «тихий» пропуск.

Принцип: агент **отказывается считать** на невалидных данных и говорит почему, вместо того
чтобы LLM «постарался объяснить» неверный результат вычислительного слоя.

## 10. Конкурентный снапшот и позиционирование

*(Требует валидации по актуальным ценам/фичам — черновик для питча.)*

| Игрок | Сила | Где мы иначе |
|---|---|---|
| BlackLine / Trintech | Close-автоматизация, сверки, enterprise-доверие | Тяжёлые, дорогие, не «агентные»; мы — быстрый AI-слой поверх данных, без миграции |
| Workday Adaptive / Anaplan / Pigment | Планирование/моделирование, крупный enterprise | Требуют внедрения и моделеров; мы — автономный аналитик на существующих данных (CSV/1С) |
| Point-AI-стартапы (variance/close боты) | Быстрые, узкие | У нас **детерминированное оптимизационное ядро (APS)** под капотом, не только LLM-обёртка |

**Позиционная гипотеза:** «Необходимый AI-слой поверх уже существующего ERP/учёта —
без миграции, с проверяемыми цифрами». Ключевой ответ на «почему не BlackLine/Anaplan»:
их надо внедрять месяцами; агент подключается к выгрузке и даёт ценность на первой неделе.

## 11. Бизнес-модель (гипотеза)

- **Модель:** SaaS-подписка **per-agent** (Analyst / Controller / Treasury / Ledger) + usage-based
  надбавка за объём (число сущностей/периодов), а не per-seat — ценность в замене работы, не мест.
- **Якорь ценности:** стоимость агента < доли FTE, которую он высвобождает (аналитик дорог,
  спрос +59%). TCO-калькулятор для клиента = маркетинговый актив (у нас уже есть ROI-калькулятор в Pricing).
- **Вход в рынок:** MVP продаётся как точечный «AI-assist for variance analysis», расширяется до пакета ролей.
- *Открыто:* точная сетка цен и порог usage — считать после PoC на реальном объёме.

| Риск | Реальный приоритет | Комментарий |
|---|---|---|
| Качество/валидация входных данных | **P0 (MVP)** | Закрыто §9 + §8 |
| Доверие к цифрам / аудит | **P0 (MVP)** | Архитектура «код считает» + аудит-трейл |
| Конкурентное позиционирование | **P1 (для питча, параллельно)** | §10; не блокер кода |
| Монетизация/TCO | **P1 (для питча)** | §11; уточнять после PoC |
| GDPR-гигиена (обработка/хранение) | **P1 (нужно к пилоту SMB)** | Базовый уровень, не полный аудит |
| SOX / полный enterprise-комплаенс | **P2 (фаза enterprise)** | **НЕ** гейтить MVP; стадировать |
| LLM-зависимость (latency/лимиты/outage) | **P2** | Цифры от кода не зависят; шаблонный fallback = дешёвая страховка, не архитектурный драйвер |
| Фрагментация / интеграции между агентами | **P2 (фаза 3+)** | На MVP агент один; риск появляется при оркестрации |
